Introduction & Problem Statement

Artificial intelligence models — particularly Large Language Models (LLMs) — are increasingly deployed as autonomous agents that must interact with external tools, databases, APIs, and services. However, there has historically been no standard way for these models to do so.

The M×N Integration Problem

Before MCP, every combination of AI model and tool required a custom integration. With M models and N tools, the ecosystem demanded M×N unique connectors — an exponentially growing maintenance burden.

⚠️
Real-world impact: A company using 4 AI models (Claude, GPT, Gemini, LLaMA) with 10 tools (GitHub, Slack, Postgres, Files, Web, Email, Jira, Notion, Stripe, Calendar) would need 40 separate custom integrations — each with its own authentication, error handling, and maintenance overhead.

Problems with the Old Approach

  • Duplicated effort across teams and organizations
  • Inconsistent APIs and authentication patterns
  • Security gaps from ad-hoc implementations
  • Vendor lock-in — switching models breaks everything
  • No shared tooling, no community ecosystem

What MCP Changes

  • Write a server once, works with every MCP-compatible model
  • Standardized authentication, error handling, discovery
  • Community-driven ecosystem of reusable servers
  • Model-agnostic — switch models without rewriting tools
  • Built-in security model with user consent

What is MCP?

"MCP is an open protocol that standardizes how applications provide context to LLMs — like a USB-C port for AI."

Model Context Protocol (MCP) is an open standard introduced by Anthropic in November 2024. It defines a universal communication protocol that allows AI models (hosts) to connect with external tools, data sources, and services (servers) through a standardized interface.

The key insight: just as USB-C standardized how devices connect to computers — eliminating a tangle of incompatible cables — MCP standardizes how AI models connect to the world.

💡
The USB-C Analogy: Before USB-C, every device had a different connector. You needed a different cable for every combination. USB-C gave one universal port. MCP does the same for AI — one protocol, infinite integrations.

Key Properties

Open Standard

Published under MIT license. Any company or developer can implement it freely. Not controlled by any single vendor.

JSON-RPC 2.0 Based

Built on the widely-supported JSON-RPC 2.0 specification — a simple, language-agnostic remote procedure call protocol.

Language Agnostic

Official SDKs for Python, TypeScript, Java, Kotlin, C#. Community SDKs for Rust, Go, Ruby, and more.

Bidirectional

Unlike simple function calling, MCP supports two-way communication — servers can also request things from the host.

Architecture Overview

MCP follows a clean three-layer architecture: a Host application containing an LLM, which connects through MCP Clients to external MCP Servers. The transport layer handles all communication between clients and servers.

4

Core Components

🏠 Host

The application the user interacts with. Contains the LLM and manages all MCP clients. Controls permissions and user consent. Examples: Claude Desktop, VS Code with Copilot, Cursor, Windsurf, custom applications.

🔌 Client

A protocol handler embedded inside the host. Maintains exactly one stateful, long-lived connection to exactly one MCP server. Handles capability negotiation and message routing. One host can have many clients.

⚙️ Server

A lightweight process that exposes capabilities — tools, resources, and prompts — to clients. Can run locally as a child process (stdio) or remotely over HTTP. Stateless or stateful depending on design.

Core Primitives

MCP defines five core primitives — the building blocks that servers expose and clients consume.

1. Tools — Model-Controlled Actions

Functions the LLM can invoke to perform actions. The AI decides when and how to call them based on the user's request. Each tool has a name, description, and JSON Schema for its input parameters.

🔧
Examples: search_web("query"), run_sql("SELECT…"), send_email(to, subject, body), create_github_pr(title, body, branch)

2. Resources — Application-Controlled Data

Read-only data exposed by the server as context for the LLM. Unlike tools, resources are controlled by the application (host), not autonomously by the model. Addressed by URIs.

📄
Examples: file:///project/src/main.py, postgres://db/users/schema, github://repo/README.md

3. Prompts — User-Controlled Templates

Reusable prompt templates and workflows that users can select and invoke. They accept parameters and return a structured message sequence ready to send to the LLM.

💬
Examples: /code-review (language, code), /summarize (document), /debug (error, stack_trace)

4. Sampling — Server-Initiated LLM Calls

The most powerful primitive. Servers can request the host to generate an LLM completion, enabling recursive, agentic loops where the AI can plan, act, observe, and re-plan.

🔄
Flow: Server → createMessage() → Host → LLM → completion → back to Server → Server continues logic. This enables fully autonomous multi-step agents.

5. Roots — Access Scope Boundaries

URIs that the client declares to the server, defining the scope of what the server is allowed to access. Roots prevent unauthorized access to files or data outside the intended working context.

🌿
Example: Declaring file:///home/user/project as a root means the server only has visibility into that directory — not the rest of the file system.

Primitive Control Matrix

PrimitiveControlled byDirectionRead/Write
ToolsAI Model (LLM)Client → ServerExecute (write)
ResourcesApplication (Host)Client ← ServerRead only
PromptsUserClient ← ServerRead (templates)
SamplingServerServer → Host → LLMRequest LLM call

Transport Layer

MCP is transport-agnostic. The same JSON-RPC 2.0 messages can flow over different transports depending on whether the server is local or remote.

🖥️ stdio (Standard I/O)

Server runs as a local child process. Host communicates via stdin/stdout pipes. Zero network overhead. Most common for local tools (filesystem, git, databases).

🌐 HTTP + SSE

Server-Sent Events for server→client streaming. HTTP POST for client→server. Supports remote servers behind firewalls. Standard for cloud-hosted MCP services.

⚡ WebSocket

Full-duplex bidirectional connection. Best for real-time, high-frequency tool interactions. Ideal when low latency and streaming responses are critical.

JSON-RPC 2.0 Message Format

Request // Client → Server: invoke a tool { "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { "name": "search_web", "arguments": { "query": "MCP protocol 2024" }, "_meta": { "progressToken": "tok-42" } } }
Response // Server → Client: tool result { "jsonrpc": "2.0", "id": 1, "result": { "content": [{ "type": "text", "text": "MCP released Nov 2024 by Anthropic..." }], "isError": false } }

Connection Lifecycle

Every MCP session follows a strict four-phase lifecycle that ensures clean initialization, capability discovery, operation, and teardown.

Phase 1 — Initialize

Client sends an initialize request containing its protocol version and supported capabilities. Server responds with its own capabilities and server information. Client confirms by sending an initialized notification.

Phase 2 — Discovery

Client calls tools/list, resources/list, and prompts/list to enumerate all capabilities the server offers. The host uses this to build the LLM's available tool namespace.

Phase 3 — Operation

Normal request/response cycles. Either side can send notifications at any time. Long-running operations report progress via notifications/progress. Requests can be cancelled with notifications/cancelled.

Phase 4 — Shutdown

Either side can initiate graceful disconnect. Server cleans up resources, client releases the connection. Abrupt disconnects (e.g., stdio EOF) are handled as implicit shutdowns.

⚠️
Important: No requests can be sent before the initialized notification is acknowledged. Any message sent before this phase completes must be rejected.

Notifications & Progress

Notifications are one-way messages — sent without expecting a response. They decouple async events from the request/response cycle.

Server → Client Notifications

MethodPurpose
notifications/progressReport % completion of a long-running tool call
notifications/messageSend a log message (debug / info / warning / error)
notifications/resources/updatedA subscribed resource has changed
notifications/resources/list_changedThe list of available resources changed
notifications/tools/list_changedNew tools became available
notifications/prompts/list_changedPrompt templates updated

Client → Server Notifications

MethodPurpose
notifications/initializedClient is ready to begin operation phase
notifications/roots/list_changedClient's root scope has been updated
notifications/cancelledCancel an in-progress request by ID

Multi-Server Architecture

A single host application can maintain simultaneous connections to multiple MCP servers. The host aggregates all tools from all connected servers into one unified namespace, which the LLM can browse and select from.

Design Rules

  • Each MCP Client maintains exactly one connection to exactly one MCP Server
  • One host can have many clients (and thus many connected servers)
  • Tool names should be unique across all servers connected to a given host
  • Servers operate independently — one server failing does not affect others
  • The host presents all tools as a flat namespace to the LLM
💡
Example: Claude Desktop connecting simultaneously to: filesystem server (local), GitHub server (local), Brave Search server (local), Postgres server (local), and a custom company API server (remote via HTTP+SSE).

Agentic Loops

MCP's Sampling primitive enables complex, multi-step autonomous agent behavior. The AI doesn't just respond — it plans, acts, observes results, and re-plans in a continuous loop.

The ReAct Pattern via MCP

  1. Plan: LLM receives the user's goal and decides what actions to take
  2. Act: LLM calls an MCP tool (search web, read file, query DB)
  3. Observe: MCP Server returns the result back to the LLM context
  4. Reflect: LLM evaluates if the goal is met; if not, re-plans and loops

Sampling Flow

Sampling enables servers to drive this loop autonomously. When a server needs to ask the LLM to reason about intermediate results, it calls createMessage(), the host forwards this to the LLM, and the LLM's completion is returned to the server — which then continues its logic.

🤖
Real Example — Autonomous Code Review Agent:
1. User: "Review and fix all bugs in my repo"
2. Agent reads files via File System server
3. Agent searches for similar known issues via Brave Search
4. Agent uses Sampling to reason about fixes
5. Agent writes fixes and creates a PR via GitHub server
6. All without manual intervention — while host shows each step to user for approval

Error Handling & Cancellation

MCP distinguishes between two types of errors: protocol-level errors (JSON-RPC transport failures) and tool-level errors (the tool ran but produced a failure result).

JSON-RPC Standard Error Codes

CodeNameWhen It Occurs
-32700Parse ErrorInvalid JSON received by server
-32600Invalid RequestJSON is not a valid RPC object
-32601Method Not FoundServer doesn't implement the method
-32602Invalid ParamsMissing or wrong-type parameters
-32603Internal ErrorServer-side execution failure

Tool-Level Errors

When a tool runs successfully (no crash) but produces a failure (e.g., file not found), the server returns a successful JSON-RPC response with isError: true in the result content. This allows the LLM to read the error message and reason about it.

Request Cancellation

Either side can cancel an in-progress request by sending a notifications/cancelled notification with the original request's ID. Servers should handle this gracefully and release any held resources.

Security Model

MCP is designed with security as a first-class concern. The protocol enforces multiple layers of protection.

🛡️ User Consent First

Every tool invocation must surface to the user via the host. Servers cannot take actions silently without user awareness and approval. The host is the trust enforcer.

🔒 Least Privilege

Servers only declare the specific capabilities they need. No broad system permissions are granted. Roots further limit file system access to declared scopes.

🔐 OAuth 2.1 for Remote

Remote MCP servers authenticate using OAuth 2.1 with PKCE. No credentials are exposed to the AI model. The host manages auth tokens transparently.

🧱 Process Isolation

Local servers run as separate OS processes, sandboxed from the host application and each other. A compromised server cannot access other servers' data.

Trust Levels

LayerWho Controls ItWhat It Protects
User consentHuman (via Host UI)Unauthorized actions
Host permissionsApplication developerWhat servers can be connected
Roots scopingClient (Host)File system access boundaries
OAuth 2.1Remote serverAuthentication & identity
Process isolationOSCross-server data leakage

Context Window Management

LLMs have finite context windows. Naively dumping all available data into the context leads to token limit errors, degraded performance, and irrelevant information. MCP enables intelligent, on-demand context loading.

Strategies

  • Lazy loading: Resources are only read when the LLM explicitly requests them via a tool call, not pre-loaded
  • Chunked resources: Large files can be paged — the LLM requests specific line ranges
  • Semantic filtering: Database servers return only rows matching the query, not entire tables
  • Server-side summarization: Servers can summarize before returning, reducing tokens consumed
  • Resource subscriptions: LLM subscribes to a resource and only receives diffs when it changes
📊
Impact: Without MCP-aware context management, a 100k token context window fills up with irrelevant data. With MCP, the same window contains only the 5-10% of data actually needed — dramatically improving accuracy and cost-efficiency.

MCP Inspector — Debugging Tool

The MCP Inspector is the official visual debugging tool provided by Anthropic for testing MCP servers during development. It provides a browser-based UI to interactively test all server capabilities.

Installation & Launch

Terminal # No installation needed — run via npx npx @modelcontextprotocol/inspector python my_server.py # For TypeScript servers npx @modelcontextprotocol/inspector node dist/server.js # Opens browser UI at http://localhost:5173

Features

  • Tools tab: Lists all tools with schemas. Click to test with custom inputs. See raw JSON-RPC request/response.
  • Resources tab: Browse all resources exposed by the server. Read content directly in the browser.
  • Prompts tab: View all prompt templates. Fill in parameters and preview the output.
  • Messages tab: Real-time log of all JSON-RPC messages exchanged between Inspector and server.

Implementation Guide

Building an MCP server takes three steps: declare tools/resources, implement handlers, choose a transport.

Python Implementation

Python from mcp.server import Server from mcp.types import Tool, TextContent, Resource import mcp.server.stdio as stdio app = Server("my-server") # Step 1: Declare tools @app.list_tools() async def list_tools(): return [Tool( name="get_weather", description="Get current weather for a city", inputSchema={ "type": "object", "properties": { "city": { "type": "string" } }, "required": ["city"] } )] # Step 2: Implement handler @app.call_tool() async def call_tool(name, arguments): if name == "get_weather": city = arguments["city"] data = await fetch_weather_api(city) return [TextContent(type="text", text=f"Weather in {city}: {data}")] # Step 3: Run with stdio transport async def main(): async with stdio.stdio_server() as streams: await app.run(*streams)

Real-World Use Cases

MCP is not a theoretical standard — it is already powering production AI applications across industries. Below are the most common and impactful use cases.

1. AI-Powered Development Environments

IDEs like VS Code, Cursor, and Windsurf use MCP to give AI assistants full awareness of the developer's environment. The AI can read any file in the project, run tests, query git history, open pull requests on GitHub, and search documentation — all through MCP servers running locally.

💻
Servers used: filesystem, github, git, postgres, brave-search, terminal

2. Autonomous Research Agents

An AI research agent can receive a topic, search the web for recent papers, download PDFs, extract key information, cross-reference findings, and produce a structured summary — all autonomously. Each capability is exposed by a separate MCP server.

🔬
Servers used: brave-search, puppeteer (browser), filesystem (PDF storage), memory (knowledge graph)

3. Natural Language Database Querying

Business users ask questions in plain English. An MCP database server translates them to SQL, executes the query against a live database, and returns structured results the LLM formats into a readable answer — no SQL knowledge required.

📊
Servers used: postgres, sqlite, mysql — whichever database the organization uses

4. Enterprise Workflow Automation

AI assistants connected to Jira, Confluence, Slack, Salesforce, and email can handle entire business workflows — triaging tickets, drafting responses, updating CRM records, and notifying teams — through a single chat interface.

🏢
Servers used: slack, jira, confluence, gmail, salesforce MCP servers

5. Code Review & Security Auditing

An automated code review agent reads every changed file in a PR, checks for security vulnerabilities, cross-references known CVEs via web search, and posts detailed review comments directly on GitHub — saving hours of manual review time.

6. Data Pipeline Monitoring

AI agents monitor production systems, query metrics from databases, check log files, correlate anomalies across multiple data sources, and automatically create incident tickets — all through MCP servers connected to the relevant infrastructure.

🎨 Creative & Design

AI manipulates Figma designs, generates images, renders previews, and manages design assets through MCP servers connecting to creative tools.

🏥 Healthcare & Research

PubMed search, clinical database queries, literature synthesis, and lab instrument data retrieval — all through domain-specific MCP servers.

MCP Configuration Guide

To use MCP servers in a host application, you configure them in the host's settings file. Here is how configuration works in the most common hosts.

Claude Desktop — claude_desktop_config.json

Located at ~/Library/Application Support/Claude/claude_desktop_config.json (macOS) or %APPDATA%\Claude\claude_desktop_config.json (Windows).

JSON { "mcpServers": { "filesystem": { "command": "npx", "args": [ "-y", "@modelcontextprotocol/server-filesystem", "/home/user/project" ] }, "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_your_token_here" } }, "postgres": { "command": "npx", "args": [ "-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb" ] }, "my-python-server": { "command": "python", "args": ["/path/to/my_server.py"], "env": { "API_KEY": "your_api_key" } } } }

VS Code — settings.json

JSON { "github.copilot.chat.mcp.servers": { "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."] } } }

Content Types & Response Formats

MCP tool call results and resource contents can carry different types of data. Understanding content types is essential for building servers that return rich, meaningful responses.

Three Content Types

📝 Text Content

Plain text or markdown. The most common type — used for query results, summaries, code output, and status messages.

🖼️ Image Content

Base64-encoded image data with a MIME type. Used for screenshots, charts, diagrams, or any visual output from a tool.

📎 Embedded Resource

A reference to a resource (by URI) or inline resource content. Lets tools return file contents without re-reading.

Text Content Example

Python return [TextContent( type="text", text="Query returned 42 rows.\n\n| id | name | email |\n|---|---|---|\n| 1 | Alice | alice@example.com |" )]

Image Content Example

Python import base64 with open("chart.png", "rb") as f: image_data = base64.b64encode(f.read()).decode() return [ImageContent( type="image", data=image_data, mimeType="image/png" )]

Multiple Content Items in One Response

A single tool call can return multiple content items of mixed types — for example, a text summary alongside an image chart:

Python return [ TextContent(type="text", text="Sales data for Q1 2026:"), ImageContent(type="image", data=chart_b64, mimeType="image/png"), TextContent(type="text", text="Total revenue: $1.2M (+23% YoY)") ]

Protocol Versioning & Compatibility

MCP uses explicit version negotiation during the initialization handshake to ensure client and server agree on a compatible protocol version before any operations begin.

Version Negotiation Flow

Version Negotiation // Client sends its supported version { "method": "initialize", "params": { "protocolVersion": "2024-11-05", "clientInfo": { "name": "ClaudeDesktop", "version": "1.0.0" }, "capabilities": { "roots": { "listChanged": true }, "sampling": {} } } } // Server responds with its version (must match or be older) { "result": { "protocolVersion": "2024-11-05", "serverInfo": { "name": "my-server", "version": "1.2.0" }, "capabilities": { "tools": { "listChanged": true }, "resources": { "subscribe": true, "listChanged": true }, "prompts": { "listChanged": true }, "logging": {} } } }

Compatibility Rules

  • If the server cannot support the client's requested version, it responds with a version it does support
  • If the client cannot work with that version, it must disconnect
  • Version strings follow a date format: YYYY-MM-DD
  • Newer clients must remain backward-compatible with older servers

Capabilities Declaration

Both client and server declare their capabilities during initialization. A capability not declared is assumed unsupported — the other side must not use it.

CapabilityDeclared byWhat it enables
toolsServerServer exposes callable tools
resourcesServerServer exposes readable resources
promptsServerServer exposes prompt templates
loggingServerServer can send log notifications
samplingClientClient supports server-initiated LLM calls
rootsClientClient can declare file system roots
resources.subscribeServerResources support change subscriptions
tools.listChangedServerServer will notify when tool list changes
⚠️
Best practice: Always check the negotiated capabilities before calling a method. Attempting to use an undeclared capability (e.g., calling resources/subscribe on a server that didn't declare resources.subscribe) should return a Method Not Found error.
