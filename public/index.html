Definition

What is MCP?

"MCP is an open protocol that standardizes how applications provide context to LLMs — like a USB-C port for AI."

Introduced by Anthropic in November 2024, MCP defines a universal language so any AI model can talk to any tool or data source — without custom glue code.

✓Open-source & community driven
✓Built on JSON-RPC 2.0
✓Language & platform agnostic
✓Reduces M×N to M+N integrations

integrations instead of M × N

Core Primitives

Four Building Blocks of MCP

🔧

TOOLS

Model-controlled actions — functions the LLM can invoke. Like function calling, but standardized across all platforms.

search_web("MCP protocol")
run_query("SELECT * FROM users")
send_email(to, subject, body)
📄

RESOURCES

Application-controlled data — files, documents, DB records exposed as read-only context for the LLM.

file:///project/src/main.py
postgres://db/users/schema
github://repo/README.md
💬

PROMPTS

User-controlled templates — reusable prompt templates and workflows the user can select and invoke.

/code-review (language, code)
/summarize (document, length)
/debug (error, stack_trace)
🔄

SAMPLING

Server-initiated LLM calls — servers can request AI completions from the host, enabling complex agentic loops.

server → createMessage() → host
host → LLM → completion
completion → server (loop)
Protocol Flow

How a Conversation Flows

① Initialize

Client connects, sends initialize request with protocol version. Server responds with capabilities.

② Capability Negotiation

Both sides declare what they support: tools, resources, prompts, sampling, notifications.

③ User Sends Message

User asks a question. LLM decides it needs to call a tool. Sends tools/call request.

④ Server Executes

MCP Server runs the tool, returns structured result. Client passes result back to LLM context.

⑤ Final Response

LLM synthesizes tool output into a natural language answer for the user.

Transport

Transport Mechanisms

🖥️

stdio (Standard I/O)

Local server runs as child process. Host communicates via stdin/stdout. Zero network overhead. Best for local tools.

Low latencyMost common
🌐

HTTP + SSE

Server-Sent Events for server→client streaming. HTTP POST for client→server. Supports remote servers behind firewalls.

Remote serversCloud-hosted
⚡

WebSocket

Full-duplex, bi-directional. Ideal for real-time, high-frequency tool interactions and streaming responses.

Real-timeBi-directional
JSON-RPC 2.0 Message Format
Request // Client → Server: call a tool { "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { "name": "search_web", "arguments": { "query": "MCP protocol 2024" } } }
Response // Server → Client: tool result { "jsonrpc": "2.0", "id": 1, "result": { "content": [{ "type": "text", "text": "MCP released Nov 2024..." }], "isError": false } }
Implementation

Building Your First MCP Server

Python from mcp.server import Server from mcp.types import Tool, TextContent import mcp.server.stdio as stdio app = Server("my-weather-server") # Declare a tool @app.list_tools() async def list_tools(): return [Tool( name="get_weather", description="Get current weather", inputSchema={ "type": "object", "properties": { "city": {"type": "string"} }, "required": ["city"] } )] # Handle tool call @app.call_tool() async def call_tool(name, arguments): if name == "get_weather": city = arguments["city"] # fetch real data here return [TextContent( type="text", text=f"Weather in {city}: 22°C ☀️" )] async def main(): async with stdio.stdio_server() as streams: await app.run(*streams)

Security

Security by Design

🛡️

User Consent First

Every tool invocation requires explicit user approval. The host enforces this — servers cannot silently act.

🔒

Least Privilege

Servers only get access to the specific capabilities they declare. No broad system permissions.

🔐

OAuth 2.1 for Remote

Remote MCP servers use OAuth 2.1 with PKCE for secure authentication without credential exposure.

🧱

Process Isolation

Local servers run as separate processes — sandboxed from the host application and each other.

5th Primitive

Roots — Scoping Server Access

Roots are URIs that the client exposes to the server, telling it "these are the boundaries you're allowed to operate within." They scope file access, databases, and any resource the server can touch.

Why Roots Matter

▸ Prevents servers from accessing unauthorized paths
▸ Client informs server of its working context
▸ Server can suggest relevant roots it needs
▸ Dynamic — can change during a session
JSON // Client declares roots to server { "roots": [ { "uri": "file:///home/user/project", "name": "My Project" }, { "uri": "postgres://localhost/mydb", "name": "Project Database" } ] }
Lifecycle

Connection Lifecycle in Detail

1

Initialization Phase

Client sends initialize with protocol version & client capabilities. Server replies with its own capabilities and info. Client confirms with initialized notification.

2

Discovery Phase

Client calls tools/list, resources/list, prompts/list to build a full map of what the server offers.

3

Operation Phase

Normal request/response cycle. Either side can send notifications. Requests can be cancelled. Progress updates flow back.

4

Shutdown Phase

Either side can terminate gracefully. Client sends no-more-requests signal. Server cleans up resources.

Async Messaging

Notifications & Progress Updates

Notifications are one-way messages — no response expected. They allow both sides to communicate events asynchronously without blocking.

Server → Client Notifications

notifications/progress — long task % complete
notifications/message — log messages (debug/info/error)
notifications/resources/updated — resource changed
notifications/tools/list_changed — new tool available

Client → Server Notifications

notifications/initialized — ready to operate
notifications/roots/list_changed — roots updated
notifications/cancelled — cancel a request
Long-Running Tool Example
JSON // Client calls a slow tool { "method": "tools/call", "params": { "name": "analyze_codebase", "_meta": { "progressToken": "tok-42" } } } // Server streams progress back { "method": "notifications/progress", "params": { "progressToken": "tok-42", "progress": 45, "total": 100, "message": "Scanning src/ files..." } }

Architecture Pattern

Multi-Server Architecture

A single host can connect to multiple MCP servers simultaneously, each exposing different tools. The LLM picks the right tool from the right server automatically.

Key Design Rules

▸ Each MCP Client connects to exactly one server
▸ One host can have many clients (many servers)
▸ Tool names must be unique across all connected servers
▸ Host aggregates all tools into one namespace for the LLM
Parallel execution Independent failures Shared context
Agentic AI

Agentic Loops — AI That Acts

MCP's Sampling primitive enables servers to request LLM completions — creating recursive, autonomous agent loops where AI can plan, act, observe, and re-plan.

Sampling: Server requests LLM

The server calls createMessage() → host forwards to LLM → completion goes back to server → server continues logic.

Real Example: Code Review Agent

1. User: "Review and fix my repo"
2. Agent reads files (FS server)
3. Agent searches for similar issues (Brave)
4. Agent creates fixes & opens PR (GitHub server)
5. Agent reports summary — all autonomous

Human-in-the-Loop

Every tool call still surfaces to the host for user approval. Agents are powerful but never act silently.

Reliability

Error Handling & Cancellation

JSON-RPC Error Codes in MCP
CodeNameMeaning
-32700Parse ErrorInvalid JSON received
-32600Invalid RequestNot a valid JSON-RPC object
-32601Method Not FoundServer doesn't support that method
-32602Invalid ParamsWrong argument types/values
-32603Internal ErrorServer-side execution failure

Tool Errors vs Protocol Errors

Protocol error — transport/JSON-RPC level (server crashed, invalid request)
Tool error — the tool ran but returned isError: true in the result content (e.g., file not found)

Cancellation // Client cancels in-flight request { "jsonrpc": "2.0", "method": "notifications/cancelled", "params": { "requestId": 42, "reason": "User interrupted" } }
Tool Error // Tool ran but failed gracefully { "result": { "content": [{ "type": "text", "text": "File not found: app.py" }], "isError": true } }

Best Practices

▸ Always set a progressToken for long tasks
▸ Use isError: true for tool-level failures
▸ Servers should handle cancellation gracefully
▸ Clients must clean up on disconnect

Context Engineering

Context Window Management

LLMs have finite context windows. MCP helps manage this by letting servers stream only relevant context rather than dumping everything into the prompt.

Smart Context Strategies via MCP

▸ Lazy loading — only read file when LLM actually asks
▸ Chunked resources — stream large files in pages
▸ Semantic search — return only relevant DB rows
▸ Summarization — server summarizes before returning

Resource Subscriptions

With resources/subscribe, the LLM gets notified when a file changes — it only re-reads the diff, not the whole file.
